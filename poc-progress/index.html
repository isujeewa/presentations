Accuracy journey - Stage 1

Each iteration came from a specific, evidence-driven change

Challenges along the way

Each step forward came from hitting a limit, understanding it, and changing approach

Challenge

We first tried CNN-based models (ResNet, EfficientNet) for Stage 1, but screenshots are dominated by text in UI context, which image-only CNNs cannot read - accuracy stalled at 34-41%.

What we did

Switched to a vision-language model that reads both the layout and the on-screen text. Qwen3-VL-8B reached 67.61% zero-shot, nearly double the best CNN.

Challenge

Public dataset labels are app-level, not screen-level - a location picker inside a weather app is labeled "Weather". Many "errors" turned out to be the model reading the screen correctly.

What we did

Reviewed misclassified images against the confusion matrix to separate real model errors from label noise, and made label cleaning a first-class workstream.

Challenge

Several categories overlap on screen content - Travel vs Maps, Education vs Books & Reference, Health & Fitness vs Medical - and no model can separate what is not separable.

What we did

Merged the overlapping pairs based on confusion evidence, going from 16 to 13 classes and lifting zero-shot accuracy to 72.36%.

Challenge

Limited local GPU memory constrained training - fine-tuning needed 4-bit quantization and reduced image resolution, and 2 epochs took ~1.5 days.

What we did

We used a smart, memory-saving technique (QLoRA) to customize the AI model using limited computer power. Even with those hardware limits, we improved the model's accuracy score by 9.92 percentage points, boosting it up to 82.28%.

We know the score can go even higher if we train it on sharper images (higher resolution) using a more powerful graphics card (larger GPU).

Challenge

A GPU model left running in the cloud costs hundreds of dollars a month even when nobody is using it - far too heavy for a POC budget.

What we did

Right-sized to a cheaper T4 GPU after first proving the model runs fast enough on it, and made the service scale to zero: a watchdog powers it off automatically after every session. Idle cost is now roughly $3/month, and a full demo session costs well under a dollar.

Phase 1 · Foundation
1

The design

  • Stage 1 - classify each screenshot into an activity category.
  • Stage 2 - a vision-language model reads the image plus the Stage 1 category and applies agreed rules to output Positive, Negative, Neutral, Risk-related or Uncertain, with supporting evidence.
  • Later phase: AWS GPU hosting, authenticated inference API, upload/results frontend.
2

Stage 1 categories

Communication, Social, Shopping, Education, Entertainment, Music & Audio, News & Magazines, Finance, Health & Fitness, Travel & Local, plus extensions (Books & Reference, Maps & Navigation, Food & Drink, Sports, Weather, Medical, Video Players & Editors, Dating, Streaming).

Stage 2 behaviors (draft)

Browsing · Messaging · Reading · Viewing media · Entering or editing content.

Known caveat from day one: RICO labels are app-store categories, so every screenshot inherits its app's label regardless of what is actually on screen. This shaped everything that followed.

Setup

4-bit NF4 quantization, FP16 compute, batch size 1 on a local GPU (~1 image/sec). Strongest classes: Maps & Navigation and Video Players & Editors (86.2%), Books & Reference (85.6%). Weakest: Travel & Local (43.9%), Education (46.3%).

Decision: use Qwen3-VL-8B as the Stage 1 base model, originally planned only for Stage 2. This opens the option of one model handling both stages in a single call.

What the images showed

  • A "Travel & Local" image was literally a Google Maps navigation screen - the model was right, the label was wrong.
  • An "Education" image was a dictionary app menu; a "Weather" image was a bare location picker.
  • 45 answers were unparsed model output; excluding them, accuracy was already 68.94%.
  • Off-list answers like "Login", "Feedback", "Alarm clock" revealed generic screens that match no category.
Conclusion: the biggest confusions were adjacent-category pairs plus app-level label noise, so merging those categories became the next step.

Phase 4 · Cloud deployment & live demo
8

What was built

  • Dedicated AWS account for the POC - clean cost and security isolation, with centrally managed admin access for the deployment team.
  • The entire environment is defined in Terraform: GPU container hosting (ECS on EC2), private image registry, model store (S3), results database (DynamoDB), and the API key held in Secrets Manager.
  • CI/CD: every push to the main branch builds the service image and deploys it automatically (GitHub → AWS with short-lived credentials, no stored secrets).
Because everything is code, the whole environment can be torn down and rebuilt on demand - and the same modules become the starting point for a production setup later.
9

What runs in the cloud

  • The validated two-stage pipeline is served as an authenticated /predict API: Stage 1 category (fine-tuned adapter) and Stage 2 behavior, each with confidence scores, in one request.
  • 1.7–2.2 seconds per screenshot for both stages on a T4 GPU (g4dn.xlarge) - fast enough that the cheaper GPU tier was locked in, instead of a ~3× more expensive one.
  • Sanity check against a hand-labeled sample: 11/12 correct on category (loose match).
  • Every prediction is stored in DynamoDB for later review.
  • Model files (~16 GB) load from S3 onto a warm cache, so a redeploy is serving again in about a minute.
10

What reviewers can do

  • Web app hosted on AWS Amplify (link shared privately) - upload a screenshot or paste an image URL and see the predicted category, behavior and confidence.
  • URL fetching happens server-side with safety guards: public image URLs only, image content only, size-capped.
  • Start/stop the GPU service from the UI: starting requires a passcode and a chosen session length (45 min / 2 h / 4 h / 8 h); stopping is one click for anyone.
  • A status bar shows whether the service is up, warming, or counting down to auto-off.
  • The inference API key never reaches the browser - all calls are proxied through the server.
